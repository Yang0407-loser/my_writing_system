# Phase 3 Batch 1 — Shadow Retrieval Report

Date: 2026-07-18
Decision: **remain in shadow mode; production retrieval is unchanged**

## Scope and invariants

This batch implemented retrieval planning and explainable reranking only. It did not change the Writer prompt, embedding provider/model, chunking, collection strategy, ContextManager, character annotations or style contract. The production path remains the legacy single-query top-5 lookup against the shared Chroma collection with a mandatory `task_id` metadata filter.

## Legacy retrieval audit

1. Writer builds one query from topic, section title, subsection title and key points.
2. `VectorStore.search_with_meta()` applies `task_id`, returns `RAG_TOP_K=5`, and optionally emits a larger diagnostic trace.
3. Those five chunks are rendered directly into the Writer prompt; causal expansion remains a later, separate step.
4. Blackboard records the retrieval trace and post-generation usage classification.

## Batch 1 implementation

- `QueryPlanner` deterministically creates at most four non-empty intents: character, event, foreshadowing and scene. Empty input returns an empty plan.
- Each intent calls the existing vector search. Results are merged by source ID (or stable text hash as fallback) into one candidate pool.
- The rules-only reranker uses vector/coarse-rank score, title and keyword match, character overlap, chapter distance, same-section duplicate penalty and mandatory future-section exclusion.
- Every candidate trace includes its source ID, matched intents, score components, final score and selection or rejection reason. Trace records hashes rather than full candidate text.
- Selection is dynamic from zero to five items. Candidates below the configured threshold are not padded with unrelated results.
- `RAG_PHASE3_SHADOW` only adds a comparison trace. Even when enabled, `writer_uses` is explicitly `legacy`, and shadow items never replace Writer input.

## Failure-layer observations

- QueryPlanner intent deviation: 15 false positives across queries 1, 2, 4, 5, 9 and 10 matched broad character or scene intents. This is an inference; intent ablation is required for causal proof.
- Vector coarse recall: all 17 false positives entered the candidate pool. Unselected candidates are not human-labeled, so missing facts cannot yet be assigned causally to coarse recall.
- Rule rerank: all 17 false positives passed threshold and final selection; 13 had a saturated character-overlap component of 1.0. This correlation makes character weighting a Batch 2 ablation target, not an automatic weight change.
- Partial fact support: 10 human-relevant chunks provided event context but supported no complete `must_recall_fact`.
- Empty result: query 3 returned zero candidates.

## Limitations and risks

- The current shadow latency is too high for production switching and should be addressed through threshold/query/token calibration or cached/shared query work only after relevance is human-validated.
- The full 5,000-chunk Chroma matrix remains under the previously documented waiver. Its triggers and the shared-collection decision are unchanged.

## Decision and next entry

Keep the implementation in shadow mode and keep `RAG_PHASE3_SHADOW=false` by default. Human review is complete, but all three retrieval-quality gates failed. The same source ID was reviewed separately when it appeared under different queries.

Phase 3 Batch 2 must not start automatically. If explicitly authorized, it should first run A/B ablations for broad intents, character-overlap saturation, threshold, query count and token budget. Unselected candidates need human labels before missing facts are causally attributed to coarse recall. Do not introduce BM25, a cross-encoder or an LLM reranker, and do not begin Phase 4.

Machine-readable human metrics and failure observations are in `reports/phase3-human-evaluation.json`; the frozen pre-review retrieval trace remains in `reports/phase3-shadow-retrieval.json`.

## Batch 2A offline diagnostic ablation

Batch 2A replayed the frozen candidate trace under 10,368 configurations. It did not call an LLM, rerun embeddings, change production code or alter any default retrieval setting. The reported precision is closed-set precision over labeled selections only; unlabeled candidates are reported separately and are never counted as irrelevant. Known-relevant retention is not a claim of true recall.

|---|---:|---:|---:|---:|---:|---:|---:|---:|
| Frozen baseline | 38 | 21 | 17 | 0 | 55.26% | 91.30% | 26.67% | 471.6 |

The result answers the Batch 2A question cautiously: broad scene/character intent and saturated character scoring explain a meaningful share of false positives, but tightening them alone does not robustly clear the 68% precision gate. The strongest in-sample precision remains 66.67% and retains only 16 of the pooled 23 known-relevant candidates; the frozen leave-one-query-out selections reach only 61.76% after review. Therefore no weight or threshold should be promoted from this ten-query diagnostic.

The two previously unlabeled candidates received Codex-assisted diagnostic review as indirectly relevant, but neither supports a complete `must_recall_fact`; fact coverage therefore remains unchanged. These are not independent human confirmations and cannot satisfy the human release gate. Their provenance-tagged labels are in `tests/quality/phase3_batch2_new_candidates_review.json`. Production remains on legacy retrieval, shadow remains the only Phase 3 path, and Phase 4 has not started.

Replay limitations are explicit: intent removal filters frozen `matched_intents`; keyword/title components are not recomputed; graded character overlap is an offline proposal; token counts come from exact stored chunk text; latency is estimated from retained query count rather than measured live. The machine-readable configuration, per-query metrics, Pareto results and leave-one-query-out folds are in `reports/phase3-batch2a-ablation.json`.

## Batch 2C real V1/V2 shadow comparison

Batch 2C added an experimental `QueryPlannerV2` and graded-character reranker without wiring either into Writer or changing defaults. V2 emits at most two queries, requires action/relation/state anchors for character queries, emits scene only for explicit place/time requirements, prevents character score from being the sole threshold reason, and caps selected context at 600 estimated tokens. It does not receive `must_recall_facts` or gold sections during planning or scoring.

The comparison executed real embedding and Chroma queries against the same shared collection with the existing `task_id` filter:

| Metric | Real V1 rerun | Experimental V2 |
|---|---:|---:|
| Selected candidates | 38 | 28 |
| Reviewed closed-set precision | 55.26% | 62.50% |
| Pooled known-relevant retention | 91.30% | 43.48% |
| Late reviewed closed-set precision | 26.67% | 20.00% |
| Gold-section candidate-pool coverage (proxy) | 76.67% | 80.00% |
| Unlabeled selections | 0 | 12 |
| Mean selected chunks | 3.8 | 2.8 |
| Mean estimated tokens | 470.3 | 317.6 |
| Mean real retrieval latency | 6107.2 ms | 4914.7 ms |

V2 is cheaper and its coarse pool covers one additional gold section, but it discards too many known-relevant query-candidate pairs. Even under the deliberately optimistic assumption that all 12 unlabeled V2 selections are relevant, pooled retention can reach only 22/35 = 62.86%, below the 90% gate. Consequently those candidates cannot change the release decision and no new reading table is requested; the generated difference artifact records 12 suppressed candidates and zero review items.

All quality gates fail except the invariant that Writer and production behavior are unchanged. V2 remains an experiment only; it is not eligible for production trial, no default setting changes, and Phase 4 remains blocked. Machine-readable traces, per-query plans, graded character evidence, real latency and the upper-bound proof are in `reports/phase3-batch2c-v2-shadow.json`.

## Batch 2D 2×2 loss attribution

Batch 2D independently executed all four planner/reranker combinations against the existing embedding service and shared task-filtered Chroma collection. Gold sections and `must_recall_facts` were used only after retrieval for evaluation and never entered planning or scoring.

| V2 planner + V2 reranker | 62.50% | 43.48% | 20.00% | 12 | 317.6 | 4869.4 ms |

The current V2 failure is shared by both modules. With the V1 reranker held constant, Planner V2 loses 9 baseline known-relevant selections. With Planner V1 held constant, Reranker V2 loses 7. In the complete V1→V2 comparison, 11 V1-selected relevant candidates disappear: 6 never enter the V2 coarse pool, 4 fall below the score threshold and 1 fails the non-character-support guard. Future exclusion, top-k and the 600-token cap directly account for zero of these losses.

No hybrid can pass all release gates even if every unknown selection is assumed relevant. The best optimistic retention upper bound among V2-planner combinations is 74.36%; the V1-planner combinations contain no unknown candidates and already fail precision/late gates. Therefore the Batch 2D review table intentionally contains zero items. QueryPlanner V2 and the current graded-reranker configuration are both rejected as promotion candidates; production remains on legacy retrieval, the experimental code stays shadow-only, and Phase 4 remains blocked.

The full loss ledger includes source ID, exact stored evidence, V1 ranks/components/final score, V2 presence/status and a bounded attribution category for every lost relevant query-candidate pair. It is stored in `reports/phase3-batch2d-loss-attribution.json`.

## Batch 2E context deduplication and evidence compaction

Batch 2E fixed the entire retrieval path to V1 and applied a new deterministic `ContextCompactor` only after selection. The component records exact source ID and character offsets, detects near duplicates using normalized sentence-set Jaccard similarity, extracts query-linked sentences with neighbors, and treats 400 tokens as a soft target rather than a truncation limit. It is not wired into Writer.

The real ten-query run retained all 38 selected sources, all 21 selected known-relevant sources, all 11 query-source items carrying `supports_which_fact`, and every late-query source. Every fragment round-trips to the exact stored source substring. However, no cross-source near-duplicate group met the 0.82 threshold, so deduplication alone removed zero characters and left the mean at 470.3 tokens.

Sentence extraction reduced the mean to 80.7 tokens (82.84%), but the apparent efficiency is invalid. Codex-assisted review of all 11 existing fact-support items found that only one still contained sufficient evidence. Ten lost essential material such as the thirty-wan funding total, explicit invitation, participation decision, delete-and-confront sequence or salty aftertaste. The most visible failure is dialogue fragmentation around Chinese quotation marks: high-scoring names and query words survive while the adjoining predicate, amount or response is cut away.

Therefore Batch 2E fails its evidence-preservation gate and is not eligible for Batch 2F diversity reranking. The 80.7-token result is retained as a negative benchmark, not a target. The implementation does not automatically restore full chunks, production remains on legacy retrieval, Writer input is unchanged and Phase 4 remains blocked. Full traces and the provenance-tagged assisted review are stored in `reports/phase3-batch2e-context-compaction.json` and `tests/quality/phase3_batch2e_fact_evidence_review.json`.

## Batch 2F structured evidence windows

Batch 2F reused the exact ten-query V1 selected-source trace from Batch 2E and compared natural-paragraph windows, dialogue-plus-narrative blocks, and 150/250/350-character windows expanded to structural boundaries. All five profiles retained 38/38 selected sources, 21/21 selected known-relevant sources and every late-query source; all output spans round-trip to exact stored source offsets. No strategy is connected to Writer or production retrieval.

| Profile | Mean tokens | Reduction vs. V1 | Codex-assisted complete fact evidence |
|---|---:|---:|---:|
| Paragraph window | 288.3 | 38.70% | 4/11 |
| Dialogue + narrative block | 346.7 | 26.28% | 7/11 |
| Character window 150 | 433.8 | 7.76% | 9/11 |
| Character window 250 | 462.7 | 1.62% | 9/11 |
| Character window 350 | 470.1 | 0.04% | 9/11 |

The two profiles that meet the 20% token target still remove necessary relation or response paragraphs. Conversely, structural character windows preserve all nine independently verifiable fact items but cover most of each chunk after boundary expansion and cannot reach the token target. Source-level budgeting is therefore not sufficient for these chunks under the current deterministic boundary rules.

The literal 11/11 gate also has a baseline ceiling that must not be attributed to compaction: source `q06-679a7aa0` contains traffic consequences and deletion but no active invitation from Zhou Ye, while `q07-679a7aa0` contains guilt and deletion but stops before Lin Wan directly faces Zhou Ye. Their original source text cannot independently prove the complete assigned `supports_which_fact` claim. The Codex-assisted review records this provenance and does not alter the existing human labels.

No profile passes all gates. Batch 2F remains a shadow-only negative result, no profile is selected, no full-text fallback is presented as success, production and Writer remain unchanged, and Phase 4 remains blocked. The next technically distinct experiment, if explicitly authorized, is parent-child or event-block chunking rather than further window tuning. Machine traces and the parallel review are stored in `reports/phase3-batch2f-structured-compaction.json` and `tests/quality/phase3_batch2f_evidence_review.json`.
