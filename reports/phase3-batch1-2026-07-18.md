# Phase 3 Batch 1 — Shadow Retrieval Report

Date: 2026-07-18
Decision: **remain in shadow mode; production retrieval is unchanged**

## Scope and invariants

This batch implemented retrieval planning and explainable reranking only. It did not change the Writer prompt, embedding provider/model, chunking, collection strategy, ContextManager, character annotations or style contract. The production path remains the legacy single-query top-5 lookup against the shared Chroma collection with a mandatory `task_id` metadata filter.

## Legacy retrieval audit

1. Writer builds one query from topic, section title, subsection title and key points.
2. `VectorStore.search_with_meta()` applies `task_id`, returns `RAG_TOP_K=5`, and optionally emits a larger diagnostic trace.
3. Those five chunks are rendered directly into the Writer prompt; causal expansion remains a later, separate step.
4. Blackboard records the retrieval trace and post-generation usage classification.

## Batch 1 implementation

- `QueryPlanner` deterministically creates at most four non-empty intents: character, event, foreshadowing and scene. Empty input returns an empty plan.
- Each intent calls the existing vector search. Results are merged by source ID (or stable text hash as fallback) into one candidate pool.
- The rules-only reranker uses vector/coarse-rank score, title and keyword match, character overlap, chapter distance, same-section duplicate penalty and mandatory future-section exclusion.
- Every candidate trace includes its source ID, matched intents, score components, final score and selection or rejection reason. Trace records hashes rather than full candidate text.
- Selection is dynamic from zero to five items. Candidates below the configured threshold are not padded with unrelated results.
- `RAG_PHASE3_SHADOW` only adds a comparison trace. Even when enabled, `writer_uses` is explicitly `legacy`, and shadow items never replace Writer input.

## Ten-query comparison

The legacy manual baseline remains P@5=68.0%, R@5=66.7% and late-chapter P@5=40.0%. Live old/new output was additionally compared with the annotated gold sections as a proxy:

| Metric | Legacy live | Phase 3 shadow |
|---|---:|---:|
| Section-proxy Precision@5 | 44.0% | 71.1% |
| Section-proxy Recall@5 | 43.3% | 70.0% |
| Late-section proxy Precision@5 | 60.0% | 60.0% |
| Mean selected chunks | 5.0 | 3.8 |
| Mean candidate pool | 5.0 | 15.2 |
| Mean estimated context tokens | 609.9 | 470.3 |
| Mean retrieval latency | 2568.9 ms | 6361.3 ms |

The shadow path reduced estimated context tokens by 22.9%, but latency increased to about 2.48 times the live legacy lookup because it performs multiple embedding/search calls.

## Release gates

| Gate | Result |
|---|---|
| Human Precision@5 ≥ 68.0% | **Unverified** — 0/38 new selected chunks exactly reuse a human candidate label |
| Section-proxy Recall@5 > 66.7% | Pass — 70.0% |
| Late-section proxy Precision@5 > 40.0% | Pass — 60.0% |
| Writer input and behavior unchanged | Pass |
| Every result explainable | Pass |

Section-proxy scores use human gold sections, but they do not establish that each returned chunk is relevant. They therefore cannot replace the human precision gate. The existing ten annotations label the old candidate snapshots; exact text-hash reuse is zero for the newly selected candidates.

## Limitations and risks

- The current shadow latency is too high for production switching and should be addressed through threshold/query/token calibration or cached/shared query work only after relevance is human-validated.
- The full 5,000-chunk Chroma matrix remains under the previously documented waiver. Its triggers and the shared-collection decision are unchanged.

## Decision and next entry

Keep the implementation in shadow mode and keep `RAG_PHASE3_SHADOW=false` by default. The review table for all 38 selected shadow chunks has now been generated at `tests/quality/phase3_shadow_candidates_review.json`. It contains the complete source chunk and retrieval explanation for each query-candidate pair, while `human_relevant`, `supports_which_fact` and `review_note` remain blank for human input. The same source ID is intentionally reviewed separately when it appears under different queries.

After human review, recompute true Precision@5. Only if the human relevance data is favorable should the next explicitly authorized batch calibrate thresholds, token budget and A/B ablations. Do not introduce BM25, a cross-encoder or an LLM reranker, and do not begin Phase 4.

Machine-readable results and per-candidate explanations are in `reports/phase3-shadow-retrieval.json`.
